# 可选扩展：为什么原项目有知识蒸馏

**本仓库已经实现邮件原件和本地搜索，但尚未实现附件全文索引、向量检索或知识蒸馏。** 以下是给对方 Codex 的实施规格，不是可以直接运行的现成功能。

## 蒸馏解决的不是“能否读信”

原项目需要长期跟进贸易案件。信息分散在不同月份、不同发件人和附件中：某个人属于哪家公司、规格改过几次、哪个报价是后来确认的、某项决定是谁作出的、下一步缺哪份资料。

蒸馏把这些材料转成有来源的长期结构：人物/组织/项目、时间线、事实候选、变更与冲突、已确认决定、待办、写作习惯。它让 Codex 少做重复的案件重建，并理解“为什么变了”。这仍是派生知识；不能取代原始邮件，也不能自动变成用户已批准的结论。

会计经常需要找原邮件、发票和对账表。**此时优先加强附件读取和检索，通常比人物关系图和长期业务蒸馏更有价值。** 金额算得对、原件找得到，比摘要很多更重要。

## 由她的 Codex 自行判断

| 实际观察 | 选择 | 判断依据 |
|---|---|---|
| 找近期邮件、发票附件、付款通知 | 现有 A+B 即可 | 已能查正文和定位原件 |
| 经常按发票号搜索，而号码只在 PDF/Excel 内 | 先加附件全文索引 | 这是“查得到”的问题，不需要知识蒸馏 |
| 邮件量很大，常用关键词不固定 | 评估语义检索 | 先拿她的真实查询测是否比精确检索更好 |
| 反复重建同一客户/账期的跨线程承诺、变更和冲突 | 小范围试点蒸馏 | 存在可复用的长期上下文 |
| 只偶尔查信，电脑性能或公司数据政策受限 | 保持现状 | 更多组件未必增加收益 |

先观察至少若干典型任务：查询次数、花时、未命中原因、附件类型、误读位置。可先用 10–20 个由用户认可的问题做小测试；这些是项目建议的验证规模，不是法律标准或现有效果数据。Codex 给出简短理由后选择最小方案，不因仓库里有这个章节就默认部署。

## 第一优先：附件全文索引

若需要，由 Codex 单独实现并验证：

1. 为选定目录和账期枚举已缓存 MIME 的附件，按 SHA-256 去重，保留每个邮件 occurrence。先做 PDF 文本、`.xlsx`、`.docx`，扫描/OFD/旧版 Office 另立待处理状态。
2. 保存 `attachment(sha256,mime,filename,size,parser_version,state,error_code)`；保存 `attachment_occurrence(account,folder,uidvalidity,uid,index,sha256)`；文本分块保存页码/工作表/单元格位置。
3. 解析只能处理副本，禁宏、脚本、压缩包自动展开；设置文件大小、页数、时间和解压后体积限制。
4. 状态至少有 `pending/extracted/needs_ocr/encrypted/unsupported/failed`。没有文字不等于空文件；扫描件去视觉核对，不把失败当成功。
5. 搜索结果带原邮件键、附件 hash、页码/单元格，财务数字引用到原件。OCR 文本是候选，金额、税额、账号、日期要检查原页。
6. 验证一批她常见的发票/对账单，包括图片 PDF、加密表格、重复附件、改名同内容和不同版本。原件保持不变。

## 第二优先：可选语义检索

不是所有账户都需要模型。Windows 先评估普通 CPU 和内存，不能照搬 Mac 的 MLX/Metal。选模型前检查公司是否允许模型下载/外部调用；索引在本机也不意味着调用 Codex 时内容不出本机。

按 `content_sha + parser_version + chunk_id + embedding_model_version` 幂等入库；精确发票号、合同号、金额查找保留精确检索。向量结果只负责找候选，最终读取原件。对照相同问题集的命中率、误命中率和延迟再决定保留。

## 第三优先：知识蒸馏实施契约

### 数据结构

至少建立以下独立派生表，不修改邮件原件表：

| 表/对象 | 必要内容 |
|---|---|
| entity | 实体 ID、类型、名称、别名；未确认身份不得强行合并 |
| claim | 主体、字段、值、候选/已确认/冲突/已取代状态、模型/规则版本 |
| evidence_ref | 账号命名空间、目录、UIDVALIDITY、UID、邮件 hash、附件 hash 与定位 |
| temporal | 邮件时间、获取时间、观察时间、生效时间；未知生效时间留空 |
| relation | claim 间 supports/contradicts/supersedes 关系，保留旧版本 |
| feedback_event | 用户采纳、修改、否定和理由；追加记录，不覆写历史 |
| distill_job | 输入 hash、批次、状态、尝试次数、检查点、错误与完成时间 |

虚构结果示例，不能导入生产账务：

```json
{
  "schema_version": 1,
  "claim_id": "demo-claim-1",
  "subject": "示例公司-九月对账",
  "field": "requested_reconciliation_date",
  "value": "2026-10-08",
  "state": "candidate",
  "effective_at": null,
  "evidence": [{
    "folder": "INBOX", "uidvalidity": "123", "uid": 7,
    "message_sha256": "<实际原件的64位哈希>",
    "excerpt": "请于10月8日前核对"
  }],
  "requires_owner_review": true,
  "external_actions": []
}
```

### 处理流程

1. 同步完成后，从已完整解析原件中挑选小批次。记录输入 hash 和原件 ID；线程历史是背景，当前发件人的正文才是这次请求。
2. 明确导出范围、模型和费用后才调用模型；可由已授权的 Codex 在当前任务中处理，不假设有另一个 API Key。
3. 模型只返回结构化候选和来源。导入前校验：每条 evidence 必须属于本批次，hash/UID 对得上，引用存在；没有来源的 claim 拒绝。
4. 金额、税率、币种、付款状态、银行账户、发票有效性等必须保持待核；模型不能替用户确认付款、入账或报税。完整邮件里明确写的“已付款”，也只是发件人的陈述，仍应与正式凭证核对。
5. 冲突并列保留，不凭“最新文件名”或摘要覆盖事实。草稿、已发送、对方回复接受、签署、实际执行分开记录。
6. 原子提交批次后才推进检查点；失败保留为可重试，不跳过。重复批次不可生成重复知识，停止后可恢复。
7. 检索先找候选知识，再读取 decisive 原邮件/附件；说明知识最后蒸馏到哪里。蒸馏落后不阻断邮件索引查询。

### 验收与退出

用人工核对的问题集验证来源可追溯、跨期冲突、重复导入、失败恢复、未解析附件、被撤回/改动的事实，以及邮件内提示词注入。对关键财务字段不容忍未经核对的自动确认。

若没有明显节省反复查证的时间，或用户需要频繁纠正摘要，停用蒸馏和派生检索；原邮件索引照常可用。不要因为已经投入时间就扩大部署。
